How it works

One command. Five steps. Nothing executed.

reticle measures selection — which tool the model reaches for — never the tool's result. Your server is read, never run against.

01

Connect

Handshake over stdio or streamable HTTP; pull every tool exactly as a real client sees it — name, description, schema.

02

Generate

A separate model writes realistic requests per tool, plus adversarial near-misses and out-of-scope noise. It never sees the eval.

03

Evaluate

Each request goes to a fresh model call with the full tool list and tool_choice=auto. It picks one — or none. Selection only.

04

Score

Per tool: picked correctly, mistaken for another (and which), or missed. Plus a confusion matrix and over-trigger rate.

05

Report

One page, worst tools first, with the real failing requests. Everything derives from a JSON artifact — every number reproducible.

Run it

A local CLI. Your key. One command.

Streamable HTTP server

# audit any hosted MCP server
reticle run --http https://their-server/mcp -n 10

Local stdio server

# or a command that speaks MCP over stdio
reticle run --stdio "npx -y server-memory"

Nothing on your target is executed. reticle lists the tools and measures which one the model would pick — it never calls them. Runs are resumable, cost is estimated before it spends, and the whole run is dumped to a JSON artifact you can re-render offline.

Why the number holds

Trustworthy enough to send a stranger.

Selection only.

Tools are never invoked. reticle measures the choice a real agent would make, so an audit can't touch your data or trigger side effects.

Separated judge.

The model that writes the test requests and the model under test are different calls with different prompts. Generation can't leak the answer.

Reproducible.

Every query, the tool-set hash, the model, and each raw pick land in one JSON artifact. The report is derived from it — never from memory.
